## Run the alpha

Install the project's dependencies and start Flask:

```powershell
python -m pip install -r requirements.txt
python app.py
```

On first start, the app creates `instance/campuspath.db` from
[`database/schema.sql`](./database/schema.sql). Set the `DATABASE_NAME`
environment variable to use a different SQLite file. The database is local
and is excluded from version control.

A fresh database starts empty, so routes are unavailable until records are
added. The included six-location seed is simulated and intended only for
demonstration; verify data before real-world use. The UI reports when there
are no locations. The old `campus.db` format is not migrated automatically;
back up and migrate any existing data before pointing `DATABASE_NAME` at it.

To load the six-location simulated dataset, first start the app once to create
the database, stop it, then run:

```sh
sqlite3 instance/campuspath.db < database/seed_demo_data.sql
```

The seed file is repeatable. Its building point coordinates come from the UMD
Campus Map's `BuildingPoint` layer; they are label points, not verified
entrances. The pathway distances, traffic scenarios, and accessibility values
are fictional demo inputs. Do not rely on them for real-world navigation.

The CampusPath assistant uses OpenAI's Chat Completions API. Set
`OPENAI_API_KEY` in the environment before starting the app; optionally set
`OPENAI_MODEL` (defaults to `gpt-4o-mini`). For example, in PowerShell:

```powershell
$env:OPENAI_API_KEY = "your-key"
python app.py
```

Or in macOS/Linux:

```sh
export OPENAI_API_KEY="your-key"
python app.py
```

Do not commit API keys. Chat messages and the current building names are sent
to OpenAI to interpret questions and route requests. The assistant is grounded
only in built-in app facts and configured building names; it does not know
unprovided campus facts. Route requests are validated and calculated by the
Flask routing API, not generated by the model. Time-of-day routing uses
`PathwayTraffic` values when present and otherwise falls back to each pathway's
baseline traffic level. Traffic levels and accessibility flags should be
verified or clearly labeled as simulated before real-world use.
The chat endpoint is unauthenticated; add rate limiting and access controls
before exposing it publicly, and monitor the OpenAI API spending limit.

## API

- `GET /api/locations` returns the configured buildings.
- `POST /api/route` accepts JSON such as
  `{"startId": 1, "destinationId": 2, "accessible": true, "timePeriod": "midday"}`.
- `POST /api/chat` accepts `{"message": "..."}` for grounded FAQ answers or
  natural-language route requests. Set `OPENAI_API_KEY` to enable it.
- Routes use Dijkstra's algorithm. Without a time period, pathway distance is
  the weight; with a period, configured foot-traffic levels affect route cost.
  The current demo weights low/medium/high traffic as 1/1.5/3 respectively;
  these are illustrative multipliers, not measured campus congestion.
  Pathways are treated as bidirectional. Accessible requests exclude pathways
  with stairs or without wheelchair access.
- Shared routing rules are defined in `route_rules.py`, the source of truth
  for route calculations and assistant explanations. `app.py` uses these
  values for routing and validation, while `chatbot.py` uses them to keep its
  explanations consistent. Update the shared module rather than duplicating
  these rules in either file.
- Walking times use a fixed 75 meters/minute baseline adjusted by traffic
  scenario values when a time period is selected. This is an estimate, not a
  trained model prediction or live traffic. `TravelTimeObservations` remains
  available for future model training.
- Route results include numbered building-to-building directions. The
  results identify the directions and distances as simulated; they do not
  provide turn-by-turn navigation.
